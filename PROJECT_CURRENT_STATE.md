# 1. Project Overview
* **Current project name:** ProjectPulse (AI-Powered Project Recommendation & Management System)
* **Purpose of the system:** To help university students form groups, find AI-recommended capstone/final-year project ideas tailored to their skills and interests, and manage the proposal and document submission lifecycle with faculty.
* **Current implementation status:** Most core features are actively implemented, including authentication, group management, AI recommendations via Groq LLM API, document uploads, and role-specific dashboards.
* **Short description of what the system currently does:** Allows students to sign up, join groups, fill in a preference form, receive 3 unique project ideas generated by an LLM, select a project, submit it to faculty for review, and upload related documents. Faculty can approve or ask for revisions. Admins can view analytics.

# 7. Database
* **Database name:** Configured via `MONGODB_URI`
* **Collections/Models (`database/models/index.js`):**
  * `User`: Stores all roles (Student, Faculty, CC_Faculty, Admin).
  * `StudentProfile`: Extended profile for students (skills, interests).
  * `Group`: Represents a team of students.
  * `Project`: Represents a submitted capstone project.
  * `Document`: Stores metadata and paths to uploaded files.
  * `Review`: Feedback and marks from faculty.
  * `ApprovedProjectArchive`: Used to blacklist already approved projects from AI recommendations.
  * `SystemConfig`: Stores dynamic settings like AI rules.

# 8. Authentication & Roles
* **Student, Faculty, CC Faculty, Admin** are implemented via `roleValues` enum in Mongoose.
* **Login/Registration:** Uses `bcryptjs` for password hashing and `jsonwebtoken` (JWT) for session management.
* **Role-based authorization:** `allowRoles(...)` middleware explicitly checks `req.user.role` before granting access to specific endpoints.

# 9. AI / Recommendation System
* **AI provider/API:** Groq API (`https://api.groq.com/openai/v1/chat/completions`)
* **Model name:** Configurable via `GROQ_MODEL` (default: `llama-3.3-70b-versatile`). Fallbacks are also configured.
* **API integration:** Implemented in `backend/server.js` (`requestGroqCompletion`).
* **Prompt logic:** A system prompt asks for exactly 3 unique projects matching the domain, difficulty, and stack provided by the student.
* **Filtering logic:** Projects from `ApprovedProjectArchive` are sent as a blacklist to prevent duplicates.
* **Currently no trained machine-learning recommendation model has been identified.** It relies completely on the external Groq LLM API.

# 11. Recommendation Pipeline
1. Student inputs preferences (Domain, Team Size, Tech Stack, Difficulty) on Frontend (`/recommendations`).
2. Frontend sends payload to `POST /api/recommendations`.
3. Backend retrieves AI rules and previously approved projects (blacklist) from Database.
4. Backend constructs a prompt and calls Groq API.
5. Groq LLM returns a JSON array of 3 project ideas.
6. Backend parses the JSON and sends it to the Frontend.
7. Frontend displays the projects on `/recommendation-results`.

# 12. Project Approval Workflow
1. Student/Group submission -> Group status becomes `SUBMITTED`, Project is created as `PENDING`.
2. Faculty review -> Faculty views submission on dashboard.
3. Decision -> Faculty clicks Approve (`PATCH .../approve`) or Request Revision (`PATCH .../request-revision`).
4. Revision -> If revision is requested, Project status becomes `REVISION_REQUIRED`.
5. Resubmission -> Student resubmits (`PATCH .../resubmit`), status goes back to `PENDING`.
6. Project locking -> Once Approved, `detailsLocked` becomes true and the project is added to `ApprovedProjectArchive`.

# 22. Current AI/ML Readiness
* **Creating a recommendation dataset:** The current `ApprovedProjectArchive` model logs approved projects. Over time, this could be exported as a JSON/CSV dataset.
* **Training an ML recommendation model:** Currently not ready. There is no historical dataset to train on.
* **Using an LLM:** Highly ready and currently actively implemented using the Groq API.
* **Similarity/duplicate detection:** Relies completely on the LLM's context window. Integrating a Vector DB (like Pinecone) would be a logical next step to make this scalable.

# 23. Recommended Next Development Step
Implement a Vector Database (like Pinecone or Milvus) to store embeddings of approved projects. This will allow for scalable duplicate detection and better RAG-based AI recommendations rather than passing the entire blacklist to the Groq API.
